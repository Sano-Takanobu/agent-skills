1. プロジェクトスキル(.claude/skills/)

リポジトリ専用の自作スキル。レビュー依頼は運用ルール上 /review-smart に一本化しており、review-and-fix / review-team-and-fix / review-adversarial の直接使用は名指し時のみ。

スキルスラッシュ形式自然言語での依頼例AIエージェントチーム構成
review-smart /review-smart [commit-range | branch] [--base <branch>] [--normal | --team | --dry-run] 「レビューして」「feature/xxx をレビューして」— レビュー依頼はこの言い方だけで起動 ルーター自身はルーティング判定とリスク階層(低・中・高)の判定のみ。review-and-fix(通常)か review-team-and-fix(チーム版)へ委譲し、高リスク差分(認証・課金・データ削除・同期・移行・非同期・クラッシュ修正・セキュリティ等)には敵対的レビュー3体を委譲先の工程に注入
review-and-fix /review-and-fix <commit-range | branch> [--base <branch>] 「review-and-fix で feature/xxx を見て」※ スキル名を明示したときのみ直接起動 単独+検証2種単独レビュアー(オーケストレーター本体)がレビュー・修正・成果物作成まで実施+独立サブエージェント2名(成果物の読者視点レビュー1名、終了時の振り返り(Retrospective)1名)。review-smart 経由で高リスク判定の場合はレビュー後に敵対的レビュー3体(読み取り専用)が注入される
review-team-and-fix /review-team-and-fix <commit-range | branch> [--base <branch>] 「レビューワーチームで feature/xxx をレビューして」※ 名指し時のみ チーム(10役)Reviewer A〜F を並列起動(A: 要件・受け入れ条件/B: クラッシュ・メモリ・非同期/C: iOS互換性・UI・a11y/D: 外部依存・Context7/E: 既存影響・設計・テスタビリティ/F: エラー処理・ビルド・運用)→ Aggregator が統合 → Self-Critique が独立検証 → 本体が修正・成果物作成 → 読者視点レビューが成果物を検証 → 振り返り。review-smart 経由で高リスク判定の場合は Self-Critique 後に敵対的レビュー3体(読み取り専用)が注入される
review-adversarial /review-adversarial <commit-range | commit-hash | branch> [--base <branch>] 「敵対的レビューだけかけて」「この差分の破綻シナリオを探して」※ 敵対的レビューを明示したときのみ。review-smart 経由の高リスク差分では同じ工程が自動注入されるため、このスキルは起動しない チーム(3役+検証2種)読み取り専用の敵対的レビュアー3体を並列起動(1: 要件・仕様破綻/2: 異常系・境界値・非同期・クラッシュ/3: セキュリティ・認証・データ破損・機密情報)→ 本体が統合・根拠の弱い指摘を除外 → Blocking(重大/高)が残る場合のみ既存の修正フローへ差し戻し → 成果物を読者視点レビューが検証 → 振り返り
review-shared (直接起動しない) 起動しない。直接依頼すると該当レビュースキルを案内 エージェントなしレビュー4スキルが参照する共通手順集。敵対的レビュー共通工程(adversarial.md)と、成果物の様式・作成後の2層検証(deliverables.md)を含む。2層検証= 層1: 形式ルールの機械チェック(ID連番・用語集カバレッジ・曖昧表現/相対比較の残存等)、層2: 読者視点レビュー。層2はチケット・コード差分・レビュー結果を渡さず成果物ファイルだけを読ませることで、外部読者(テスト会社のテスト設計者)の前提知識ゼロの状態を再現し、作成者側では気づけない欠落を検出する
crashlytics-daily /crashlytics-daily 「今日のクラッシュ監視をやって」「過去24時間のクラッシュ状況を確認して」 単独Firebase MCP でデータ取得〜分類〜レポート保存まで1名で完結
crashlytics-report /crashlytics-report <期間> 「6月分のクラッシュレポートを作って」「5/1〜5/31 の Top10 とクラッシュフリー率をまとめて」 単独
crashlytics-analyze /crashlytics-analyze <issue-id> 「この Crashlytics issue を詳しく分析して」「issue xxx の根本原因を調べて」 単独直接原因・根本原因・再現条件・影響範囲を1名で分析
crashlytics-fix /crashlytics-fix <issue-id> 「issue xxx の分析結果をもとに修正して」「このクラッシュを直してテストも書いて」 単独最小スコープ修正+ユニットテスト適用
ga-audit /ga-audit [出力先ディレクトリ(省略可)] 自然言語では起動しない(disable-model-invocation)。明示的に /ga-audit と打ったときのみ チーム(7役)アプリの計測実装(Google Analytics / Firebase Analytics)をローカルのソースコードだけを根拠に棚卸しする監査スキル(完全読み取り専用・管理画面/MCP/Web検索は不使用、リポジトリは非改変)。専用サブエージェントを段階起動: sdk-scout(分析SDK・ラッパー層・ユーザープロパティ)+ event-cataloger(イベント定義と全呼び出し箇所の機械的列挙のみ・解釈は禁止 → JSON)を並列 → flow-analyst 複数体(担当イベントを明示分割し、意味・トリガー・送信条件・呼び出し経路を並列分析)+ quality-auditor(未使用・重複・命名揺れ・計測漏れ・パラメータ不整合・PII懸念)→ verifier(独立検証)→ business-strategist(ファネル・KPI・セグメント軸への非エンジニア向け翻訳)→ reporter(検索・絞り込み・印刷対応の単一HTMLレポート生成)。verifier は成果物を見る前に別の grep パターンで一覧を再導出して突き合わせ、根拠の パス:行番号 を実際に開いて裏取りし、秘密情報・個人情報の混入を機械検査したうえで、修正指示を機械適用可能な JSONで返す(オーケストレーターは判断せず適用のみ)。全記述は 確認済み/推定/改善提案/要確認 の4分類タグ付きで、実データなしに効果・数値を断定しない
plan-review /plan-review [企画書パス(md/PDF/pptx/画像・複数可) | Redmineチケット番号] 「この企画書に意見書を出して」「チケット #xxxx の企画をレビューして」(テキスト貼り付けも可) チーム(8役)Expert A〜F を並列起動(A: 要件定義/B: 仕様整合性/C: 実装可能性・アーキテクチャ/D: 規模見積もり・フェーズ分割/E: UX・既存導線/F: リスク・審査)→ 本体が統合 → 独立検証役サブエージェント+振り返り
dev-loop /dev-loop <Redmineチケット番号>[#note-<コメント番号>] [修正ループ上限回数] 自然言語では起動しない(disable-model-invocation)。明示的に /dev-loop と打ったときのみ チーム(ループ型・ゲート付き)オーケストレーターが QAエンジニア役・開発者役(同一コンテキストのロールプレイ)を進行し、設計者とレビューワーは独立サブエージェントとして起動。設計者は仕様解釈を「明記/推論/仮定」に全件分類した設計プランを作成し、オーケストレーターが実装前ゲートで判定する。設計・API・データモデル・ユーザー可視の挙動を左右する「仮定」が残る場合はコードを書かせずに人間判断へ回す。ゲート通過後の実装はプラン準拠(解釈に関わる逸脱は停止・軽微な逸脱は逸脱ログへ記録)。レビューNG→開発者へ差し戻す修正ループ(既定2回)を制御。#note-N 指定時は、チケット全体ではなく当該コメントを仕様の一次情報として扱い(チケット本文・他コメントは背景情報)、出力先も別フォルダに分離する
release-history /release-history <新タグ> [<前タグ>] 「v1.2.3 の変更履歴を README に追記して」「リリースタグをもとに変更履歴を更新して」 単独

スキルスラッシュ形式自然言語での依頼例AIエージェントチーム構成
agent-ops-weekly /agent-ops-weekly [--since YYYY-MM-DD] 「棚卸しして」「agent-ops レビュー」「週次棚卸し」 単独レビュー系・plan-review・dev-loop・crash-rca の自己改善データ(学習候補・提案カード・Phase)を週次で棚卸しし、昇格・採否をユーザー承認のもとで反映
competitor-weekly /competitor-weekly [比較対象レポートのパス](省略時 latest.md) 「競合レポートを作って」「週次の競合ウォッチを実行して」 単独+検証本体が情報収集〜差分レポート生成。検証(A)決定論スクリプト+検証(B)別モデル点検の二重ゲートを通過後にスライド(pptx)生成へ進む
qiita-series-editor /qiita-series-editor(依頼内容は文章で指定) 「シリーズに編入して」「親記事を更新して」「シリーズを監査して」「次に書くべき記事は?」 単独+検証編集長(本体)が編入・監査・相談の3モードを判定。編入モードでは書き込み前に校閲サブエージェント(general-purpose)を必須で起動
crash-rca /crash-rca <Redmineチケット番号 | Crashlytics issue URL> 自然言語では起動しない(disable-model-invocation)。明示的に /crash-rca と打ったときのみ チーム(6〜7役・逐次)Redmineチケット または Crashlytics issue URL 起点のクラッシュ根本原因調査(iOS・完全読み取り専用)。オーケストレーター本体が専用サブエージェントを逐次起動: ticket-analyst(チケット事実確認・Redmine起点のみ)→ crashlytics-analyst(issue・stack trace分析)→ code-mapper(stack traceとコード照合)→ hypothesis-builder(原因仮説)→ falsifier(独立反証)→ reporter(レポート統合)。Crashlytics URL 起点ではチケット確認を省き、URL から抽出した issue ID(sessionEventKey も活用)の深掘りから開始する。仮説を作る者と反証する者を別エージェントに分離
work-intake /work-intake <SlackメッセージまたはスレッドURL> 自然言語では起動しない(disable-model-invocation)。明示的に /work-intake と打ったときのみ チーム(2〜4役)Slack 上の相談・不具合報告・調査依頼の受付窓口(完全読み取り専用)。専用サブエージェントを起動: thread-reader(スレッド収集)→ link-reader(Redmine・GitHub・資料リンクの確認)。判断に必要な場合のみ Explore 最大2体で影響範囲を補足調査。事実・推測・未確認事項・影響範囲・担当領域・チケット化要否を「受付票」に整理し、既存スキル(review-smart / crash-rca / plan-review / dev-loop 等)への推奨コマンド、または該当スキルが無い場合の Redmine 起票文案を提示する。後続スキルは自動起動せず、推奨コマンドの提示まで(Slack 投稿・チケット更新・コード変更もしない)
